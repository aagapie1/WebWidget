# Threat model

Status: started in E5 B9 with the audit log. The full model (assets, actors, entry points,
controls, remaining risks with owners) is E5 D16.

## Audit log (E5 B9, ADR 015)

**Asset:** the record of who changed a client's assistant, with what result. For an institution,
it is evidence.

| Threat                                                                 | Control                                                                                                                                                                                                                                                        | Remaining risk                                                                                                                                                                           |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The application (or an attacker in it) edits or deletes records        | `widget_app` has only `SELECT, INSERT` on `audit_log`; each record is hash-chained to the previous one; `audit-verify` finds any change, insertion, removal or gap.                                                                                            | —                                                                                                                                                                                        |
| Someone with database owner access rewrites a whole chain consistently | Daily anchors: the last hash of every chain, signed with Ed25519, stored outside the database next to the backup and off-site. `audit-verify --anchors` finds a chain that no longer contains an anchored head. The private key is not on the database server. | Changes made after the last anchor and before the next one are detectable only from the next anchor on. An attacker holding both the database and the anchor key can rewrite undetected. |
| Retention deletion used to hide records                                | Only the cleanup role deletes, only a prefix of a chain, and records `retention.purge` (last deleted position and hash) in the same transaction. Minimum retention 6 months.                                                                                   | A super-admin can lower a client's period to 6 months (recorded in the chain).                                                                                                           |
| Wrong or manipulated times                                             | Times come from the database clock in UTC. The host keeps NTP synchronisation (`timedatectl`: `System clock synchronized: yes`, `NTP service: active`, `Time zone: Etc/UTC`; checked 2026-11-19, deployment README). Containers use the host clock.            | A host with a stopped NTP service drifts until the next check.                                                                                                                           |
| A spoofed IP in the records                                            | The client IP comes from `X-Forwarded-For` only when the request arrives from `TRUSTED_PROXIES` (Traefik's network, D1); otherwise the socket address.                                                                                                         | —                                                                                                                                                                                        |
| One client's administrator reads another client's log                  | The chain is chosen on the server from the session's organisation; other chains return 403 and the attempt is recorded in both chains. Tested end-to-end (isolation test).                                                                                     | —                                                                                                                                                                                        |
| Keycloak events lost (failed sign-ins not in the log)                  | Imported every minute with deduplication; an alert after 5 minutes of failure, and a recovery record with the interval. Keycloak keeps events 7 days. The reader account has only `view-events`.                                                               | An import outage longer than 7 days loses events.                                                                                                                                        |
| Events lost while the database is down                                 | Configuration changes are written in the same transaction as their record (no change without a record).                                                                                                                                                        | Sign-ins, views and denials are best effort: lost while the database is unavailable (`audit_write_failed` in the logs).                                                                  |
| Exported copies leak administrators' personal data                     | Export only for widget-admin and super-admin; every export is recorded with who took it and what.                                                                                                                                                              | Once downloaded, a copy is the client's responsibility (privacy notice, E7).                                                                                                             |
