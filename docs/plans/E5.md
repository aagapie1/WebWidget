# E5 — security and anti-abuse (plan)

Status: **approved 2026-11-19**, with the changes in "Approval" at the end. Mandatory
before the first public client. Source: docs/SPEC.md §5 (E5), the requests of 2026-11-19 and the
E5 items of docs/BACKLOG.md. The order of stages changes: E5 now, E4b.2 after it (the backlog said
E4b.2 first; updated when E5 starts).

**[DECIDE]** marks a choice to confirm before implementing; **[SCHEMA]** a configuration change
(new optional fields only; existing YAML files and published versions stay valid); **[ADR]** a
decision written down in docs/adr/.

## A. Public surface (widget and /api)

### A1. Loader styles without `style-src 'unsafe-inline'` (ADR 010)

- The loader's CSS becomes a constructable stylesheet (`new CSSStyleSheet()`, `replaceSync`,
  `shadowRoot.adoptedStyleSheets`): CSSOM, which `style-src` does not restrict.
- Fallback where `adoptedStyleSheets` is missing: `<link rel="stylesheet">` in the Shadow DOM to
  `/w/loader.<hash>.css`, served by the gateway with the loader's cache rules (the same text, built
  from one source).
- The per-client values that are set today with `style` attributes (`--cw-accent`, offsets…) move
  to a second constructed sheet (`:host { --cw-accent: … }`), so no inline style attribute remains.
- The chat iframe (`/w/app`, served by the gateway) is checked too: its own CSP must not need
  `'unsafe-inline'` for styles either (Preact's `style` props become classes or CSSOM).
- **e2e**: a test page with a strict CSP (`default-src 'none'; script-src <gateway>;
style-src <gateway>; frame-src <gateway>; connect-src <gateway>; img-src <gateway>`), in
  Chromium, Firefox and WebKit: the launcher is styled, opens, the chat works, no CSP violation
  reported (`securitypolicyviolation` listener). Plus the fallback path, forced.
- "Integrare pe site": `cspFor()` lists `style-src <gateway>`; the `'unsafe-inline'` note goes.
- Budget: `loader.js` stays under 15 KB gzip (13.9 KB today).

### A2. Origin / Referer and `frame-ancestors`

- A table test over every public endpoint (`/w/loader.js`, `/w/app`, `/api/loader-config`,
  `/api/widget-config`, `/api/chat`, `/api/chat/stop`, `/api/conversations*`, feedback, tenant
  assets): allowed origin, another origin, no origin, `Origin: null`, preview tenants.
- `/w/app`: when a `Referer` is present, its origin must equal `parent` (one more signal; it is
  not required, since `Referrer-Policy` may strip it). Enforcement stays `frame-ancestors`.
- **[DECIDE] D1** — trusted proxies: `trustProxy` only for the Traefik network
  (`TRUSTED_PROXIES=172.16.0.0/12` style), so a client cannot fake its IP through
  `X-Forwarded-For` (rate limits depend on it). Recommended.

### A3. Rate limits, message and conversation limits

- One shared limiter (the admin's Redis counters, moved to a common module), keyed by IP and by
  visitor (the signed visitor cookie). Proposed defaults, all **[DECIDE] D2**:

  | What                        | Per visitor            | Per IP       |
  | --------------------------- | ---------------------- | ------------ |
  | messages (`/api/chat`)      | 20 / minute, 200 / day | 60 / minute  |
  | new conversations           | 10 / hour              | 30 / hour    |
  | feedback and comments       | 30 / hour              | 100 / hour   |
  | conversation list / history | 60 / minute            | 120 / minute |

- Message length: 4000 → **2000** characters **[DECIDE] D3** (Dify's answers are the long part;
  questions over 2000 characters are almost always pastes).
- **[SCHEMA]** optional `limits` per client (super-admin only, like the name), for clients with
  shared IPs (an institution behind one NAT): only raises or lowers the defaults within bounds.
- Answer: `429` with `rate_limited`, `Retry-After`, and which limit (`scope: message | conversation
| …`). The widget shows a localized, polite message ("Ați trimis multe mesaje într-un timp
  scurt. Puteți continua în 40 de secunde."), announced once, the question kept in the field,
  the send button disabled until then.

### A4. Anti-bot without third parties

- **[DECIDE] D4** — **ALTCHA** (MIT): proof-of-work, solved in a Web Worker in the chat iframe,
  verified by the gateway with an HMAC secret; no image, no audio, no interaction, nothing loaded
  from a third party (the solver is bundled; the challenge comes from our gateway). Alternative:
  our own SHA-256 proof-of-work (no dependency, more code to maintain). Recommended: ALTCHA's
  server library for challenges and verification, our own small solver in the worker (keeps the
  app bundle small).
- **Only above thresholds**: below the soft limits nothing changes. Over a soft threshold (e.g.
  half the per-IP limit, or a new visitor starting many conversations) new conversations need a
  solved challenge; difficulty grows with abuse.
- Accessible: a polite status "Se verifică…" while solving (usually under a second), no timeout
  shorter than 30 seconds, works without a mouse; a clear message if it fails, with "Încercați
  din nou".

### A5. Logs without personal data

- `maskPersonalData` gains IBAN (RO and generic `[A-Z]{2}\d{2}[A-Z0-9]{11,30}`), and card numbers
  (13–19 digits with spaces) **[DECIDE] D5** (cards: yes, recommended; cheap and useful).
- Applied to: feedback comments (today), any text that reaches a log, and the error details from
  Dify before logging.
- A pino safety net: `redact` for known fields, plus a log formatter that masks every string
  value. Tested with sample data (fictitious CNP, phone, e-mail, IBAN, card) sent as messages,
  comments and error texts: the captured log output contains none of them.

## B. Administration

### B6. Organisation lookup (`/admin/auth/org`, from the backlog)

- Its own per-IP limit (10 / 10 minutes) and a global limit (300 / 10 minutes), Redis.
- The same answer time for found and not found (a fixed minimum duration, e.g. 200 ms).
- Alert: a structured warning log `org_lookup_burst` (IP hashed) when the not-found answers of an
  IP or of all IPs pass a threshold. **[DECIDE] D6** — the alert channel: log-based for now (the
  server's log monitoring picks it up), a Prometheus metric later (NFR backlog). Recommended.

### B7. `/admin` only from given networks

- A Traefik `ipAllowList` middleware on the `/admin` router, from `ADMIN_ALLOWED_IPS` (optional:
  empty = no middleware). Keycloak is not behind it (it is the identity provider, reached by the
  clients' users). The preview iframe is under `/admin` too, so it follows.
- Checked by a compose test (`docker compose config` with and without the variable) and documented
  in the deployment README.

### B8. Cookies, CSRF, session length, forced logout **[ADR]**

- Verify and write down (ADR 014): cookie flags per environment, CSRF scheme, session length per
  realm (`sessionHours`), idle timeout, what a password change or a disabled account does.
- Forced logout from the server: **[DECIDE] D7** —
  - OIDC **back-channel logout** from Keycloak (Keycloak calls the gateway when a session ends or
    a user is disabled; the gateway ends its sessions for that `sid`/`sub`): recommended;
  - plus a CLI for the platform team: `pnpm admin:sessions revoke --user <sub> | --tenant <id>`.
    Both need a Redis index of sessions by user and by tenant.

### B9. Detailed audit log and its screen (moved from E4b.2, 2026-11-19)

Requested by public institutions. Placed right after D1: the IP must be trustworthy before it is
recorded. Today the log keeps `draft.save`, `draft.discard`, `publish` (with the diff),
`origins.change` and `asset.upload`, with who (issuer, subject, name), append-only for the
application role.

**What each event records** **[SCHEMA: database migration 003]**

- when: `at` in UTC (`timestamptz`), shown in Romanian time (`Europe/Bucharest`) in the screen and
  the exports; the server clock synchronised by NTP (host `chrony`/`systemd-timesyncd`, checked in
  the deployment README and the threat model; containers use the host clock);
- who: Keycloak user id (`sub`) and issuer, name, e-mail, role, organisation, and the sign-in
  source (`local` account or the institution's IdP alias, from the token's `identity_provider`
  claim, mapped in each realm);
- from where: IP (after D1), user-agent (truncated to 512 characters), a session id **hash**
  (SHA-256 of the session id, never the session itself) and the request's correlation id;
- what: action, section, changed fields with old and new values (the existing diff), published
  version ("versiunea 2"); `sensitive: true` for allowed domains;
- result: `success`, `denied` (with a reason: `forbidden`, `draft_conflict`, `invalid`,
  `rate_limited`) or `failed`.

**Events**

- sign-in (success, refused: no role / wrong realm, failed callback), sign-out, session expired —
  recorded by the gateway itself;
- from Keycloak: failed passwords, temporary lockouts, password changes, IdP sign-ins, and admin
  events (realm changes) — user events and admin events enabled in every realm, then **imported**
  (see K1);
- draft saved, published, discarded, image uploaded and image deleted (see K6), allowed domains
  changed (sensitive);
- access denied: an editor publishing, a request to another client, an organisation-level
  forbidden;
- the audit log viewed and exported (see K7).

**Integrity: hash chain** — each record stores `prev_hash` and `hash = SHA-256(prev_hash ‖
canonical JSON of the record)`; inserts serialised by an advisory lock per chain (see K2). A
command `pnpm --filter gateway db:audit-verify [--tenant id]` recomputes the chain and reports the
first broken record. The database keeps `REVOKE UPDATE, DELETE` for the application role.

**Screen "Jurnal de audit"** (a new admin area, visible to `widget-admin` for their organisation
and to `super-admin` for every one; not to editors, also refused by the API)

- list (newest first, paged) with filters: period, user, action, section, result, and a search
  (user, field, value); times in Romanian time;
- an event's detail: who, from where, result, and the diff old → new per field (domains marked
  sensitive);
- export CSV and JSON of the filtered list for auditors (UTF-8, ISO times in UTC plus a local time
  column; JSON includes `prev_hash`/`hash` so the auditor can verify the chain); the export itself
  is recorded.

**Retention** — 12 months by default (D12), configurable per client within 6–60 months
**[SCHEMA] `audit.retentionMonths`, super-admin only**; the daily cleanup job (C13) deletes older
records with its own database role and records a `retention.purge` system event (see K3).

**GDPR** — an ADR: legal basis legitimate interest (security and accountability, art. 6(1)(f)),
the data (identity, IP, user-agent), the period, who can see it; the text for the client's privacy
notice goes to E7.

**Tests** — unit (chain, canonical JSON, masking of nothing important by mistake), API (isolation
between clients, editors refused, filters, export formats, verify command catching a modified
row), e2e: filters, detail with diff, export CSV/JSON (contents and the export event), isolation
between clients (pilot cannot see demo-primarie, even by a direct request), keyboard and axe.

## C. Production and infrastructure

### C9. Production compose (`deploy/docker-compose.yml`)

- Traefik: TLS with Let's Encrypt (**[DECIDE] D8** HTTP-01, or DNS-01 if port 80 is not reachable
  from the internet), redirect 80 → 443, HSTS (`max-age=31536000; includeSubDomains`, no preload
  at first).
- Redis: a named volume, **[DECIDE] D9** persistence — **AOF `appendfsync everysec`** recommended
  (sessions and counters change often; at most a second lost), RDB as the alternative (simpler,
  minutes lost). Written in an ADR.
- Postgres: a named volume; a `backup` service running `pg_dump` daily (custom format,
  compressed) into a host directory that the server's restic plan picks up; 7 daily dumps kept
  locally; a restore script and a restore test in the deployment README.
- **[DECIDE] D10** — Keycloak in this compose? The spec puts "Keycloak on the server, shared with
  the Dify console" in E4b.2. Recommended: include it now (the admin cannot work in production
  without it), with its own Postgres database, and leave the Dify console SSO to E4b.2.

### C10. Hardened containers

- Gateway image: multi-stage build, `pnpm deploy --prod`, Node 22 on a slim base, user `node`
  (non-root), no build tools at runtime.
- Every service: `read_only: true` with `tmpfs` where needed, `security_opt:
no-new-privileges:true`, `cap_drop: [ALL]` (Traefik adds only `NET_BIND_SERVICE`), memory and
  CPU limits, healthchecks (`/healthz`, `redis-cli ping`, `pg_isready`, Traefik ping).
- Checked by a script over the composed configuration (each service has these settings).

### C11. Secrets

- Only from env files (`deploy/secrets/*.env`, mode 600, git-ignored) or Docker secrets; the
  gateway reads `*_FILE` variables (Docker secrets convention).
- Nothing in images or git: `scripts/check-secrets.mjs` scans the git tree (Dify `app-` keys,
  private keys, passwords in YAML), the built image (`docker save` layers, `docker history`) and
  the env file permissions; runs in CI and before deploy. **[DECIDE] D11** — also gitleaks in CI
  (a widely used scanner, binary pinned by checksum): recommended as a second opinion.

### C12. Security headers on every answer

- A common Fastify hook: `X-Content-Type-Options: nosniff`, `Referrer-Policy`
  (`strict-origin-when-cross-origin` for the widget, `no-referrer` for the admin and the API),
  `Permissions-Policy` (everything off; `microphone=(self)` reserved for the chat iframe when voice
  arrives, E8), CSP on every route type (API: `default-src 'none'; frame-ancestors 'none'`).
  HSTS from Traefik.
- A test over every route type checks the headers; the ZAP scan (D15) double-checks.

### C13. Data retention

- Server settings with defaults: audit log 12 months, drafts 90 days without changes, feedback per
  client (90 days, exists), sessions (exists), cited documents and installations 90 days (exist).
- A cleanup job: `gateway/src/cli/db.ts cleanup`, run daily by a small compose service. The audit
  log is append-only for the application role (by design), so the job uses a separate role with
  `DELETE` on old audit rows only (`audit_cleanup`), never the application's credentials.
  **[DECIDE] D12** — audit default 12 months (as requested) and configurable 6–60 months.

## D. Supply chain and verification

### D14. Dependencies and images

- `pnpm audit`: blocking on **critical**, a warning on high (today: blocking on high — **[DECIDE]
  D13**: keep blocking on high, recommended, since it has not blocked anything unfixable so far).
- Image scan with Trivy (action pinned by commit SHA), blocking on critical; SBOM (CycloneDX)
  generated at build and kept as a CI artifact.
- **[DECIDE] D14** — **Dependabot** (built into GitHub, no app to install) recommended over Renovate;
  weekly, grouped (dev dependencies together), security updates at once. Each Playwright/axe-core
  update re-checks the Firefox crash (backlog).

### D15. DAST

- OWASP ZAP baseline against the gateway started with the e2e configuration (fake Dify, test
  tenants), in CI, with a rules file for accepted findings (each with a reason).
- **[DECIDE] D15** — report-only for the first two weeks, then blocking on medium and above.
  Recommended (a baseline scan's first run usually needs tuning).

### D16. Threat model

- `docs/security/threat-model.md`, short: assets (conversations, admin access, Dify keys, client
  configurations), actors (visitors, bots, a malicious site embedding the widget, a client's
  admin going beyond their client, an insider at the platform), entry points, the controls of
  this stage, and the remaining risks with owners.

## Approval (2026-11-19)

Approved with these changes:

- **D1 first, as a separate fix.** It is an existing vulnerability: `X-Forwarded-For` is believed
  from anyone, which bypasses every rate limit (the admin sign-in included). The client IP comes
  from `X-Forwarded-For` only when the connection comes from a trusted proxy (the Traefik
  network, a configurable list); otherwise the connection's own address. With a test.
- **D2** as proposed; the default table stays in A3, and the limits are configurable **per client**
  (`limits`, super-admin only).
- **D3** 2000 characters by default, configurable per client.
- **D5** card numbers masked only when they pass the **Luhn** check (no false positives on other
  long numbers).
- **D8** HTTP-01, with a dependency to settle: **port 80 must be open at the provider** (today it
  does not answer from outside). DNS-01 stays documented as the alternative.
- **D10** Keycloak is **a shared service of the server** (`/srv/shared`, next to Traefik), with one
  realm per client, later also used for the Dify console's SSO. The gateway only connects to it;
  the gateway's compose does not start it. The layout goes in an ADR.
- **D13** `pnpm audit` blocking on high and critical.
- D4, D6, D7, D9, D11, D12, D14, D15 as recommended. E4b.2 comes after E5.

Order: D1 fix first, then the order above (A1 …).

**Change of 2026-11-19:** the audit log screen moves from E4b.2 into E5 as **B9**, right after D1
(the IP is recorded only once it can be trusted); its decisions K1–K8 wait for approval.
